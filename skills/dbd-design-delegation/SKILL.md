# AI に仕事を任せるための作業流儀

前提: AI に任せた仕事の失敗は、モデルの能力不足よりも、渡した文脈の設計不良から起きることのほうが多い。品質は、仕事の切り方・文脈の渡し方・完了の決め方で作る。

## いつ使うか

- AI エージェント / 自動化 / ワークフローを新しく設計するとき (リポジトリの雛形を作るときを含む)
- 既存の仕組みに作業単位や自動化の範囲を足すとき
- 設計や実装をレビューするとき

## 連携するスキル

本スキルは **中身** (任せ方の規約と構造) を見る。形と運用は次に任せる。

| 場面 | 任せる先 | 引き渡すもの |
|---|---|---|
| 7 つの置き場所のうち 宣言 (skills/) に SKILL.md を書く・直す・レビューする | `dbd-write-skill` | 本スキルが決めた原則・不可侵・構造の中身。形 (フロントマター・9 ブロックの順序・受け入れ条件) はそちらの規則 A〜E に従う |
| 検証 (evals) を実際に走らせる、あり/なしで比較する、description を最適化する | `skill-creator` | 単位ごとの evals の初版 (生成 / レビュー / 不可侵 / 非発火) |
| 成果物が文書・スライド・表などのファイル | その形式のスキル (docx / pptx / xlsx 等) | 出力の形と検証の方法 |

分担の規則: 中身の不適合 (原則に反する、任せる範囲を広げている、置き場所が混ざっている) は本スキルが指摘する。形の不適合は dbd-write-skill の判定を引用し、本スキルでは重複して指摘しない。両方に反するときは形を先に直す。

## 進め方

設計・実装・レビューのいずれでも、次の 6 原則を順に当て、満たさない点を指摘または修正する。

1. **決めてから動く** — 仕様と分解を先に固定し、確定するまで実行しない。計画の出力に実行に必要な情報をすべて含め、実行側で考え直させない。実行中に判断を変えたくなったら計画に戻る。
2. **単位は原子的に** — 各作業単位は単独で完了・検証・やり直しができる大きさ。単位間の依存は実行順として明示。新しい単位は既存と同じ形で 1 つずつ足す。
3. **文脈は薄く、新鮮に** — 単位ごとに文脈を開き直し、必要な仕様と参照だけ渡す。共通規約は一か所に置き参照で引く。入口の指示書に手順や閾値を書き戻さない。
4. **指揮は薄く、作業者が働く** — 指揮役は「何を・どの順で・誰に」だけ。決定論的に計算できるものは道具に出し、AI に計算させない。作業者の定義に責務と「やらないこと」を明記。
5. **完了は検証で決める** — AI の「できた」を根拠にしない。機械で確かめられるものは機械で。外部への書き込みは影響度で分岐 (軽微=自動 / 重大=人の承認後 / 判断=人が行う)。取り消せない操作は実行前に内容を提示し、明示の許可があるときだけ。
6. **成果物を正とする** — 仕様・計画・結果・決定の記録が記憶であり、会話は記憶ではない。正本システムを一つ決め、連絡手段は報告と承認にだけ使う。記録は追記で残す。

6 つは連鎖している (1→2→3→4→5→6)。どれか一つを緩めると他も緩む。

## 一線

AI に任せる範囲は影響度として設計時に固定する。AI は影響度を上げられるが下げられない。範囲を広げる根拠は運用の記録 (予測の的中率・提案の承認率) から取り、広げる決定は人が基準を編集して行う。この点を緩める提案には必ず反対し、代わりに記録を根拠にした見直し手順を示す。

## 構成ファイル構造 (7 つの置き場所)

原則をディレクトリで表す。置き場所は「変える人と頻度が違う」で分ける。新しくリポジトリを起こすときはこの形で雛形を作り、既存をレビューするときはこの形とのずれを指摘する。

```
<repo>/
├── skills/                  宣言 — 作業単位の入口 (薄く: 名前・いつ使うか・権限・参照のみ)      原則 3
│   ├── <prefix>-core/      共通規約への入口 (直接は呼ばない)
│   ├── <prefix>-<unit>/    単位ごと (<unit> は <動詞>-<目的語>)
│   ├── <prefix>-approve-<unit>/  承認ゲート (人が明示的に呼ぶ。自動起動しない)
│   └── <prefix>-review-<unit>/   記録のレビュー (読み取り専用)
├── agents/<prefix>-<role>.md 役割 — 作業者の責務 / 入出力 / やらないこと。指揮役は順序だけ    原則 4
├── core/
│   ├── workflows/<unit>.md 手順 — 検知→分析→立案→実行→学習→報告                       原則 1
│   ├── references/         基準 — 単位ごとの閾値表、影響度、出力契約、信頼境界、取り込み規約、記録の形  原則 2/5/6
│   ├── templates/          人に見せる文面の雛形、設定の例
│   └── bin/                計算 — CLI + lib (単位の純関数 / 正本・連絡手段・取り込み・記録の I/O / 描画)  原則 4/5
├── fixtures/ tests/ evals/  検証 — 正本と同じ形のサンプル、単位ごとの赤/緑テスト、振る舞いの評価   原則 5
├── README.md AGENTS.md      案内 (人向け / AI 向け)
└── <runtime>/ (Git 管理外)  固有データ — 設定、取り込み文書、直近の結果、追記ログ                    原則 6
```

置き場所ごとの規則:

- 宣言: 手順と閾値を書かない。権限は最小。書き込む入口は自動起動しない。SKILL.md の形は dbd-write-skill に従う
- 手順: 数値は道具から受け取る。step の出力形式はここが正
- 基準: コードの定数と同値を保つ。片方だけ変えない
- 計算: 単位ロジックは I/O を持たない。書き込みは実行内容を先に返し、明示の指示でのみ行う
- 役割: 「やらないこと」を必ず書く。指揮役に判断を足さない
- 検証: 外部サービス無しで全経路が回る。検査を消して通さない。evals の実行と比較は skill-creator
- 固有データ: Git に入れない。会話を正にしない。記録は追記のみ

### 置き場所ごとの命名

名前は「一覧で所属と役割が分かる」ために付ける。仕組みごとに短い接頭辞 (2〜4 文字) を 1 つ決め、外から呼ばれる入口 (宣言・役割) にだけ付ける。内部の置き場所 (手順・基準・計算・検証) はディレクトリで所属が分かるので接頭辞を付けない。同じ作業単位は全置き場所で同じ `<動詞>-<目的語>` を使い、単位名を grep すれば 7 か所すべてが出るようにする。

| 置き場所 | 形 | 例 (接頭辞 `xx`、単位 `check-expense`) |
|---|---|---|
| 宣言 `skills/` | `<接頭辞>-<動詞>-<目的語>/SKILL.md`。承認ゲートは `<接頭辞>-approve-<目的語>`、レビューは `<接頭辞>-review-<目的語>` | `skills/xx-check-expense/SKILL.md` |
| 役割 `agents/` | `<接頭辞>-<役割名>.md`。役割名は行為者の名詞 1〜2 語 (…er / …or)。指揮役は `<接頭辞>-orchestrator` | `agents/xx-expense-checker.md`, `agents/xx-orchestrator.md` |
| 手順 `core/workflows/` | `<動詞>-<目的語>.md`。宣言の name から接頭辞を除いたものと一致 | `core/workflows/check-expense.md` |
| 基準 `core/references/` | `<主題>.md`。単位の閾値表は `<動詞>-<目的語>.md` で手順と同名 | `core/references/check-expense.md`, `core/references/impact-levels.md` |
| 雛形 `core/templates/` | `<成果物名>.md`。人に見せる文面はその文書名を大文字で | `core/templates/approval-request.md`, `core/templates/REPORT.md` |
| 計算 `core/bin/lib/` | `<動詞>-<目的語>` または `<主題>` で拡張子は言語のもの。単位の純関数は手順と同名 | `core/bin/lib/check-expense.<ext>` |
| 検証 `tests/` `fixtures/` `evals/` | `<単位名>.test.<ext>`、fixture は正本と同じ形の名前、evals は `<単位名>/evals.json` | `tests/check-expense.test.<ext>` |
| 記録 `docs/adr/` `docs/features/` | `<課題番号>-<kebab-slug>.md` (決定)、`<kebab-slug>.md` (機能)。番号は課題管理の正本が振る | `docs/adr/0042-impact-levels.md` |
| 固有データ `<runtime>/` | 大文字の文書名 `LOG.md` `RESULT.md` など。会話由来の名前を付けない | `<runtime>/LOG.md` |

規則: 接頭辞は仕組み内で 1 つ (MUST)。宣言と役割以外に接頭辞を付けない (MUST NOT)。宣言の name は動詞-目的語で、名詞だけの名前にしない (MUST。形の詳細は dbd-write-skill B1')。同じ単位は全置き場所で同じ `<動詞>-<目的語>` (MUST)。

## 作業単位を 1 つ足すとき

単位名 `<unit>` = `<動詞>-<目的語>` を先に決め、同じ形で 7 か所に足す。順番は依存の向きどおり。

1. `core/bin/lib/<unit>` — 純関数 (THRESHOLDS → evaluate → detectSignals → proposals → analyze)。出力契約に従う
2. `core/references/<unit>.md` — 閾値表 (1 と同値)、影響度の対応
3. `core/workflows/<unit>.md` / `agents/<prefix>-<role>.md` / `skills/<prefix>-<unit>/SKILL.md` (SKILL.md は dbd-write-skill の雛形で)
4. CLI の単位一覧と描画に登録
5. `tests/<unit>` — fixture で赤と緑の両方。fixture を変えたら他単位の期待値も更新
6. 指揮役の実行順と横断論点に組み込む
7. `evals/` に 1 件 (指示・期待・機械検査)。実行は skill-creator

## レビュー時のチェックリスト

- 何ができたら終わりかが 1 段落で書かれているか (原則 1)
- どの単位のどの置き場所を変えるか決まっているか (原則 2)
- 入口の指示書に手順や閾値が書き足されていないか (原則 3)
- AI に計算させる箇所が増えていないか (原則 4)
- 検査が足され、本番への書き込みなしで検証されたか (原則 5)
- 実行時のデータや会話を根拠にしていないか (原則 6)
- 影響度を下げる変更が含まれていないか (含むなら記録の根拠があるか) (一線)
- 7 つの置き場所のどれかに、別の置き場所のものが混ざっていないか (例: 宣言に手順、計算に I/O、固有データが Git に)
- 名前が置き場所ごとの命名に従っているか (接頭辞は宣言と役割だけ、宣言は動詞-目的語、同じ単位は全置き場所で同名) (原則 2/3)

## 出力の形 (既定: レビュー)

設計のときは原則ごとに「この設計ではこうする」を 1 行ずつ書き、続けて 7 つの置き場所に何を置くかをツリーで示し、末尾に検証の方法を 1 行添える。レビューのときは満たさない原則と置き場所のずれだけを、該当箇所と修正案つきで列挙する。満たしているものは列挙しない。SKILL.md の形に関する指摘は dbd-write-skill の判定を引用する。
